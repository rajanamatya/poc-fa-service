# Architecture

This document explains the structure and reasoning behind this codebase.
Read this before writing any code. Read it again when something feels wrong.

---

## Stack

**Initial setup (vue-project-setup skill):**
- Vue 3 + TypeScript (browser target)
- Vue Router + Pinia (wrapped — see Stores)
- shadcn-vue + Tailwind CSS
- Storybook
- Vitest
- localStorage as the data layer during development

**Added when deploying to AWS (aws-deploy skill):**
- AWS Lambda + API Gateway (Node target)
- AWS S3 + CloudFront (SPA hosting)
- AWS CDK (infrastructure as code)

## Core philosophy

**Presentation and logic are completely separate.**

Dumb components only render. Smart components only coordinate.
Stores only manage state. Composables only orchestrate.
Pages only compose.

If a file is doing more than one of those things, it is in the wrong place.

---

## Key terms

These terms are used throughout the codebase and this document.

**Dumb component** — a component that only renders. It receives data
via props and communicates upward via emits. It has no knowledge of
stores, services, or application state.

**Smart component / Container** — the single component in a module
that owns state coordination. It imports store wrappers, composes
loading flags, and passes data down to dumb components. Named
`[Feature]Container.vue`.

**Module** — a folder in `src/components/modules/` that groups one
Container and its related dumb components into a self-contained feature.

**Store wrapper** — a composable that is the public API for a domain.
Exposes readonly state and named actions. Wraps a raw Pinia store so
consumers never interact with Pinia directly.

**Reducer** — a pure function that transforms state. Same input always
produces the same output. No side effects, no API calls.

**Orchestration composable** — a composable that coordinates actions
across two or more store wrappers, or encapsulates a multi-step workflow.

**Effects composable** — a composable that manages page lifecycle:
fetching on mount, resetting on unmount, reacting to route changes.

## Directory structure

```
my-project/
│
├── src/                    # Vue SPA — browser target
│   ├── components/
│   │   ├── ui/             shadcn-vue primitives — rarely touched
│   │   ├── blocks/         reusable building blocks — render only
│   │   ├── modules/        feature folders — one Container + dumb components each
│   │   └── layouts/        slot-based page structure — no logic
│   ├── stores/             one folder per domain
│   ├── composables/
│   │   ├── orchestration/  cross-domain workflows
│   │   └── effects/        page lifecycle and route reactions
│   ├── utils/              shared utilities
│   ├── router/
│   └── pages/              route-level composition
│
├── functions/              # Lambda handlers — Node target (scaffolded by aws-deploy)
│   └── [domain]/
│       └── handler.ts
│
├── shared/                 # Contract layer — types only (scaffolded by aws-deploy)
│   └── types/
│
├── cdk/                    # CDK infrastructure (scaffolded by aws-deploy)
│
├── stories/                # mirrors src/components/ — visual coverage
│   ├── blocks/
│   ├── modules/
│   ├── layouts/
│   └── tsconfig.json       # @/* → ../src/* alias for TS language server
│
└── tests/                  # mirrors testable layers — logic coverage
    ├── src/
    │   ├── stores/
    │   ├── composables/
    │   ├── components/
    │   └── utils/
    └── functions/
```

### The mirror rule

`stories/` and `tests/` deliberately mirror `src/`. A missing folder
is an intentional architectural statement, not an oversight.

| src/ layer | stories/ | tests/ |
|---|---|---|
| `src/components/ui/` | — | — |
| `src/components/blocks/` | ✅ | — |
| `src/components/modules/` | ✅ dumb components only | ✅ Container only |
| `src/components/layouts/` | ✅ | — |
| `src/stores/` | — | ✅ `tests/src/stores/` |
| `src/composables/` | — | ✅ `tests/src/composables/` |
| `src/utils/` | — | ✅ `tests/src/utils/` |
| `functions/` | — | ✅ `tests/functions/` |
| `shared/` | — | — (compiler is the test) |

## Component layers

### ui/
shadcn-vue primitives live here. Generated by the CLI and lightly
customised via `globals.css` tokens. Treat as a dependency — do not
add business logic here.

### blocks/
Dumb, reusable building blocks. A block is a label + input + error
message, an avatar, a status badge. It has no knowledge of any domain.

- No store imports
- No internal logic
- Always has a story
- Never has a test

### modules/
Self-contained features. Each module folder contains one Container
and one or more dumb display/form components.

- Dumb components: story only
- Container: test only

### layouts/
Pure structure. Named slots define regions. No props, no state,
no logic. Pages decide what fills the slots.

## Functions

> These files are scaffolded by the `aws-deploy` skill. They do not exist until you run that skill.

Lambda handlers live in `functions/` as a peer to `src/`. The backend
follows a CQRS split: one Lambda for reads, one for writes.

- Compiled independently by CDK `NodejsFunction` + esbuild
- Node 22 target — no browser APIs
- Pure handler functions — testable without AWS
- Designed to scale to ~15 functions
- Tests live in `tests/functions/`

```
functions/
├── query/
│   └── index.ts         # GET /contacts, GET /matters — DynamoDB Scan
└── command/
    └── index.ts         # POST/PUT/DELETE — DynamoDB Put/Delete
```

Each handler dispatches on `event.resource` and `event.httpMethod`.
Table names are injected as environment variables from CDK.

## Shared types

> These files are scaffolded by the `aws-deploy` skill. They do not exist until you run that skill.

`shared/` is the contract layer between the Vue app and Lambda functions.
It is owned by neither — both depend on it.

- Plain TypeScript only — no Vue, no AWS SDK
- No test files — the TypeScript compiler is the test
- A type error in `shared/` surfaces as a compile error in both layers simultaneously

```
shared/
└── types/
    ├── api.ts           # ApiResponse<T>, PaginatedResponse<T>
    ├── contact.ts       # API-layer Contact / ContactFormValues (dates as strings)
    ├── matter.ts        # API-layer Matter / MatterFormValues (dates as strings)
    ├── commands.ts      # ContactCommand / MatterCommand discriminated unions
    └── index.ts
```

Types in `shared/` use JSON-safe primitives — dates are `string | null` (ISO 8601)
throughout. Display components format date strings for presentation; no conversion
happens in the service layer.

## Infrastructure

> This infrastructure is scaffolded and deployed by the `aws-deploy` skill. Run it once all domains are working locally with localStorage.

```
CloudFront Distribution
  ├── Default behavior    → S3 bucket (SPA assets)
  └── /api/* behavior     → API Gateway origin
        └── CF Function   strips /api prefix at viewer-request
```

The SPA makes all API calls as relative paths (`/api/contacts`, `/api/matters`).
CloudFront matches the `/api/*` path pattern, runs a CloudFront Function to strip
the prefix, then forwards the request to the API Gateway origin. From the browser's
perspective there is a single origin — no CORS headers are needed.

### Local development mirrors production exactly

The Vite dev server is configured with a proxy that replicates the CloudFront routing:

```ts
// vite.config.ts
server: {
  proxy: {
    '/api': {
      target: 'https://<api-gateway-url>',
      rewrite: (path) => path.replace(/^\/api/, ''),
      changeOrigin: true,
    }
  }
}
```

The SPA code calls `/api/contacts` in both environments. In development the Vite proxy
strips the `/api` prefix and forwards to API Gateway. In production CloudFront does the
same thing via the CloudFront Function. **No application code changes between environments** —
switching is controlled entirely by the `VITE_USE_LOCAL_STORAGE` env var.

The `shared/` types are path-aliased (`@shared/*`) in both `vite.config.ts` and
`stories/tsconfig.json` so the same imports resolve correctly in the app, in stories,
and in the IDE without any conditional logic.

**CDK stacks:**

| Stack | Resources |
|---|---|
| `ApiStack` | API Gateway REST API, Query Lambda, Command Lambda, ContactsTable, MattersTable |
| `HostingStack` | S3 bucket, CloudFront distribution, `/api/*` behavior + CF Function |

## Containers

A Container is the single smart component in a module. It is the
boundary between your application state and your presentation layer.

**It owns:**
- Store wrapper imports
- Loading flag composition
- Emit handling from dumb children
- Navigation — via `useRouter()` when views are route-driven, or a local `ref` for transient UI state that does not need a shareable URL

**It never:**
- Imports raw Pinia stores
- Calls services directly
- Contains business logic
- Has a Storybook story

### Navigation state: router vs. local ref

Prefer the router when the view state should produce a shareable URL
(e.g. `/contacts/view/:id`). Use a local `ref` only for transient state
that does not belong in the URL (e.g. a confirmation modal open/close).

**Never put navigation state in the store.** Whether a contact is being
viewed or edited is a UI concern, not a domain concern. The store owns
data; the router or container owns where the user is.

### When to add a composable

A container should stay simple. If it starts growing beyond
coordinating one store and one view toggle, extract a composable.

**Use an orchestration composable when:**
- The container needs two or more store wrappers
- A multi-step workflow spans multiple domains
- Derived state requires data from multiple domains

**Use an effects composable when:**
- Data needs fetching on mount
- State needs resetting on unmount
- The container reacts to route param changes

## Stores

Plain Pinia is not enough on its own — it provides reactivity but
no conventions. Without conventions, every developer answers the same
questions differently. The store wrapper pattern encodes the team's
agreement about how Pinia gets used.

Each domain has four files:

| File | Purpose |
|---|---|
| `use[Domain]Store.ts` | Public API — readonly state + named actions |
| `[domain]Reducers.ts` | Pure state transforms — no side effects |
| `[domain]Service.ts` | External calls — internal to wrapper only |
| `types.ts` | Domain types and initial state |

### Key rules

- The wrapper is the only public API — services are never exposed
- All state is `computed()` or `readonly()` — consumers cannot mutate
- Reducers are pure — same input always produces same output
- Stores never import other stores — use orchestration composables
- Every async action follows the loading/error pattern consistently

### reducerPipeline

`src/utils/reducerPipeline.ts` composes reducers in sequence.
Named deliberately to avoid confusion with CI/CD pipeline tooling.

```ts
store.$patch(pipeline(normalizeReducer, setActiveReducer)(state, payload))
```

## Styling

shadcn-vue defines design tokens as CSS variables in `src/assets/globals.css`.
`tailwind.config.ts` maps every token to a Tailwind color utility using the
`<alpha-value>` placeholder, which enables the full range of Tailwind modifiers.

**Use tokens for design decisions:**
```html
<!-- ✅ Correct — works in light and dark mode -->
<div class="bg-card text-card-foreground">

<!-- ❌ Wrong — breaks dark mode -->
<div class="bg-white text-gray-900">
```

**Use Tailwind for layout and spacing:**
```html
<div class="flex gap-4 p-6 w-full">
```

**Opacity modifiers work on all token colors:**
```html
<div class="bg-primary/50 text-foreground/75">
```

**Hover and focus variants work on all token colors:**
```html
<button class="bg-primary hover:bg-primary/80 focus:ring-2 focus:ring-primary">
```

**Content scanner rule — always use complete class name literals:**

Tailwind's scanner reads raw file content with regex — it does not execute
JavaScript. Dynamic class names built from partial strings are invisible to it
and will be missing from the build with no error.

```ts
// ✅ Correct — full literals, scanner finds them
const swatches = [
  { bg: 'bg-primary/100' },
  { bg: 'bg-primary/50' },
]

// ❌ Wrong — scanner never sees bg-primary/100
const stops = [100, 50]
// template: :class="`bg-primary/${stop}`"
```

When a new token is added to `globals.css`, a matching entry must be added
to `tailwind.config.ts`.
